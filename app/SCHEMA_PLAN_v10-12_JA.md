## 2. 今の作り（コードで確かめたこと）

### 2-1 データ本体と表

- データ本体は 1 つのスプレッドシート（`Trends2Targets_Data`）です。1 表 = 1 シート、1 行目に英字の列名、値はすべて書式なしのテキストで持ちます（`Store.js`）。
- 表の列は `Schema.js` の `APP_TABLES` だけで決まります。今の版は 9（`APP_SCHEMA_VERSION`）です。
- 版を上げると、最初の操作（`Setup.js` の `appAutoEnsureTables_`）が無い表を作り、`_SCHEMA` に版と列のハッシュを書きます。
- **今ある表に列を足す仕組みはありません。** 1 行目が定義と違う表は、読み書きを止めます（`appTableSheet_`・`appCheckTableHead_`）。版 3〜9 は、どれも表を足しただけです。
- 使わなくなった表は消さずに隠します（`APP_RETIRED_TABLES`）。

### 2-2 書き方

- 計画への書き込みは、書き終えた後の中身を控え（ジャーナル）に置いてから書きます（`Journal.js`。書き方は replace・replacePlan・ensure・patch の 4 つ）。途中で止まっても、次の書き込みの前に控えのとおり書き直します。
- 追記（ensure）は、表の全部の行を読んでキーの有無を確かめてから足します（`appEnsureRows_` → `appInsertRows_`）。表が大きくなるほど遅くなります。
- `plan_id` の列がある表は、締めた年度の計画の行を、どの道でも書けません（`YearClose.js` の `appRequireOpenJournalOps_`）。
- 1 列目が `plan_id` の表は、3,000 行を超えると計画の行だけを探して読みます（`appReadPlanTable_`）。
- 書くたびに、読んだ結果の控え（CacheService）の印 `APP_DATA_GEN` を 1 つ変えます。どの表に書いても、全部の画面の控えが古くなります（`appBumpGen_`。記録つきの操作の終わりでも変えます）。
- 書き込みはスクリプト全体の鍵 1 つで順に行います（待つのは 30 秒まで。`APP_LOCK_WAIT_MS`）。裏の処理（予測など）も全体で 1 つずつです（`Jobs.js`）。

### 2-3 記録と監査

- 操作ごとに、開始と終了を年度のログ（`Trends2Targets_Logs_FYyyyy`）に鎖つきで残します（`Audit.js`）。
- 入力の保存は、開始の行に「保存した行」が入ります（4 万字まで）。前の値は入りません。ログは年度ごとのファイルで、画面からまとめて読む作りではありません。

### 2-4 上限

| 上限 | 中身 | 今の作り |
|---|---|---|
| セル 1000 万 | データ本体の全部のシートの「行 × 列」 | 毎日の手入れで空の行を減らす（`appOrganizeDataBook_`。最後の行 + 200 行を残す）。足すときは 1,000 行ずつ増やす |
| 1 セル 5 万字 | 1 つのセルの文字数 | 4 万字を超える JSON は、先頭とハッシュだけにする（`appJson_`） |
| 年度の控え 8MB | 年度を締めるとき、`plan_id` の列がある表の、その年度の行を全部 1 ファイルに写す（`YearSnapshot.js`） | 超えると締めずに止まる（元の行はそのまま） |
| 1 回 6 分 | 裏の処理の 1 段 | 続きの処理に分ける（`__next`） |

- 目安（読み取り専用の写しで数えたもの。名前と金額は見ていません）: 今の 1 計画は十数万セル、年度の控えで 1〜2MB です。大半は売上と実績の明細（`ENG_SALES_INPUT`・`ENG_ACTUAL_EVAL_MONTHLY`）です。
- 売上の取り込み（A-2）は年度の前の 48 か月を、実績の取り込み（B-1）は前の 3 年と今年度を、計画ごとに写して持ちます（旧来の `importMonthlyFromExternal_`）。

### 2-5 消えている記録

| もの | 今の書き方 | 残っているもの |
|---|---|---|
| 入力（製品・メーカー全体・見解・スポット） | 保存のたびに表ごと置き換える（旧来の `webSaveInputs`）。売上の取り込み（A-2）も行のひな形を書き足す（`refreshManualInputSheets_`） | 監査の開始の行の「保存した行」だけ（4 万字まで・前の値なし） |
| AI 調査（`AI_RESEARCH_STRUCTURED`） | 調べるたびに全部消して書き直す。週 1 回の自動の調査も同じ | 話題ごとの点数（`AI_SCORE_HISTORY`）だけ。根拠の文は、前の回のものが残らない |
| 層ごとの効き | 円で分けた効きは OUTPUT にだけあり、次の予測で上書きされる。`FORECAST_SNAPSHOT` の `subjective_adj`・`ai_adj` は、旧来の計算がいつも 0 を書く | 回ごとの月の真ん中（混合と客観。`FORECAST_MONTHLY`）、人と話題ごとの押しの率（`SUBJECTIVE_IMPACT_HISTORY`）、AI の倍率（`AI_IMPACT_HISTORY`）。根拠の画面は一番新しい回だけを組み立てる（`Basis.js`） |
| 予算の下書き | 予測し直すと、採用予測は月の真ん中に、上乗せは空に戻る（旧来の OUTPUT の作り直し） | 公式版を出した分だけ（`PLAN_VERSIONS`） |
| 公式版の前提 | 数字だけ | 届く見込み・幅・τ・w は残らない |

## 3. 版 10（決定 9・13・14・15）

### 3-0 版 10 の共通の決まり

1. **追記だけ。** 行は消さず、書き換えません。直すときは新しい行を足します（数え方を変えたら `calc_version` を上げて足します）。例外は人のつなぎ（3-6）で、ROLES と同じく「無効」の印だけを変えます。
2. **計画ごとの表は 1 列目を `plan_id` にします。** 大きくなっても計画の行だけを読めます。締めた年度の行は自動で書けなくなり、年度の控えにも自動で入ります。
3. **書くのは今ある操作の中だけです。** 本体の保存と同じ控え（ジャーナル）に「追記」を足して一緒に書くので、本体と記録が食い違いません。新しい自動の処理とメールは足しません（週 1 回の自動の AI 調査は今あるものです。その保存の中で書くだけです）。
4. **追記の速さ:** キーの列だけを読んで重なりを確かめる書き方を `Store.js` に足します（今の ensure は表を全部読みます）。
5. **1 セルは小さく:** JSON は 1 行分の小さいものにします。4 万字で切り詰められた行が無いことを、テストで確かめます。
6. **試しの値は記録の表にだけ書きます。** `ENG_*`・OUTPUT・`FORECAST_*`・`PLAN_VERSIONS` の数字は変えません。
7. **記録は計算に使いません。** 学びが予測に効くのは承認の後だけです（決定 16。版 10 では、まだ提案も作りません）。
8. **見せる範囲はサーバーの応答で絞ります**（今の `appPlanViewFor_`・`appBasisFor_` と同じ作り）。

### 3-1 入力の記録 `INPUT_LOG`（決定 15）

保存のたびに、変わった行だけを「前と後」で残します。

| 列 | 中身 |
|---|---|
| `plan_id` | 計画 |
| `log_id` | 記録の番号（INL-時刻-乱数）。**キー** |
| `action_id` | その操作の番号（`PLAN_ACTIONS` の `action_id`。計画を作ったときは、その番号） |
| `action` | 操作（入力の保存・売上の取り込み・計画を作る・移行のときの姿 BASELINE） |
| `kind` | product・client・opinions・devspot |
| `change` | ADD（足した）・CHANGE（変えた。同じ印の組の上の行を外して `#n` だけ詰まった行の付け直しも CHANGE）・REMOVE（外した）・CONF（自信だけ変えた）・BASELINE |
| `row_key` | 行の印（種類・担当者・製品・月・スポットの名前。同じ印が 2 行あれば #2 を付ける。欄の値の `%`・`\|`・`#` は `%25`・`%7C`・`%23` にして、区切りの `\|` と `#n` と取り違えない） |
| `person` | 担当者の欄（入力のまま） |
| `before_json` | 変える前の行（月・増減率・確度・金額・理由など）。足したときは空。`#n` だけ詰まった行の CHANGE と、出どころで組んで担当者・製品・月を変えた行の CHANGE には、前の印を `_key` に入れる（画面には送らない） |
| `after_json` | 変えた後の行。外したときは空 |
| `self_conf` | 自信（任意。製品とメーカー全体の行だけ。高い・ふつう・低い）。**計算には使いません** |
| `reason` | 保存の理由（任意・200 字まで） |
| `signal_id` | 書き写した情報の番号（版 12 から使う。それまで空） |
| `actor_email` | 保存した人 |
| `saved_at` | 保存した時刻 |

| 項目 | 中身 |
|---|---|
| 書く操作 | 入力の 4 つの表（`ENG_PRODUCT`・`ENG_CLIENT`・`ENG_OPINIONS`・`ENG_DEV_SPOT`）が変わる保存と実行のすべて（入力の保存・売上の取り込み・計画を作る）。`Forecast.js` の `appChangedOps_` で前の行と後の行を比べ、変わった行だけを同じ控えで足します |
| 自信の欄 | 入力の画面で選びます。旧来の表（PRODUCT・CLIENT）の列は変えず、この記録にだけ書きます（旧来の計算は読みません）。画面には、その行の一番新しい記録の自信を出します。画面は選び直した行だけ自信を送り、送らない行は今の自信のままです（古い画面の保存で、ほかの人が変えた自信を戻さない） |
| 前と後の組み方 | 入力の保存では、画面が保存ごとに `fromRows: true` を、行ごとに「開いたときの何行目から来たか」（`fromRow`。0 から。足した行には無い）を送り、それで組みます（`fromRow` の無い行は ADD、どの行の出どころにもならなかった行は REMOVE。開いたときの行を全部外して足した保存も同じ）。`fromRows` を送らない保存（前の画面）は、どれかの行に `fromRow` があればそれで組み、どの行にも無ければ、入力のハッシュを確かめない保存・ほかの操作と同じく、同じ印どうし・同じ位置で組みます。見分けられない行（中身も跡も同じ。手を付けていないひな形など）は入れ替えても同じなので、同じ印だった行を先に組み、無くなる印の方を外したことにします |
| 同じ印の組 | 同じ印の組（`#2`・`#3`…）の行を外すと、下の行の `#n` が詰まります。出どころで組んだ行の印が `#n` だけ変わったら、その行の自信と跡はその行についていきます: 自信は前の印の自信と比べ（ほかの行の自信と比べて CONF を足さない）、新しい印に CHANGE（中身は同じ・`before_json` の `_key` に前の印・その行の自信）を足します。画面の跡は、その CHANGE から前の印の跡（その保存より前）をたどり、外した行やほかの行の跡は付けません。出どころで組んで担当者・製品・月を変えた行も、CHANGE の `_key` に前の印を入れ、跡はその行自身の前の跡をたどります（前にその印を使ったほかの行・外した行の跡を付けない）。同じ位置で組んだ保存の CHANGE で印が変わったものは、跡をそこで止めます。付け直しだけの CHANGE は画面の跡に出しません。新しい印のもとの行と中身も跡も同じなら足しません（見え方が同じ）。足した行（ADD）の跡は ADD から始まります |
| 見る画面 | 予測の「入力」（行ごとの変わった跡。カーソルで出す）、当たりの記録の計算（3-4）、版 12 の書き写しの照合 |
| 増え方 | 保存 1 回につき変わった行の数だけ。目安: 1 計画 年 300 行・約 4,500 セル |
| 残し方 | 消しません。年度を締めると年度の控えに入ります |
| 見られる人 | 予算策定担当以上（そのメーカーの担当を含む）。閲覧の人には送りません（入力の表の担当者名は今までどおり出します） |

| テスト | 保存 1 回で変わった行だけが足される／A-2 でひな形が足されたときも記録される／控えの書き直しで二重にならない／旧来の表に自信の列が入らない／閲覧の人の応答に入らない／切り詰めの行が無い |

### 3-3 層ごとの効き `LAYER_EFFECTS`（決定 15）

予測 1 回 × 月ごとに、「統計の土台 → スポット → 人 → AI → 補正 → 最後の値」を円で残します。

| 列 | 中身 |
|---|---|
| `plan_id` | 計画 |
| `effect_id` | 予測の回と月から作る印。**キー** |
| `run_id` | 予測の回（`FORECAST_RUNS`） |
| `ym` | 月 |
| `final_p50` | 最後の真ん中（`FORECAST_MONTHLY` の値と同じ） |
| `stat_p50` | 統計の土台（過去の売上だけ。人の入力を含めない） |
| `spot_yen` | 人が入れたスポット案件の効き |
| `human_yen` | 製品・メーカー全体・見解の効き |
| `human_by_type_json` | その種類ごとの内訳（人の名前は入れない） |
| `ai_yen` | AI 調査と Vertex の効き |
| `calib_yen` | 補正の効き（係数と月ごとの補正） |
| `other_yen` | 分け方で合わない分（足すと必ず `final_p50` になるようにする） |
| `method` | 分け方（LMDI か RATIO。下の注） |
| `source` | forecast_open（予測の月）か actual_closed（締まった月で、実績に置き換えた行） |
| `recorded_at` | 書いた時刻 |

- 分け方の第一案: 旧来の計算にすでにある「主観の寄与の分解」（CONFIG の `LMDI_DECOMPOSITION_ENABLED`、今は 0）を 1 にし、予測の保存のときに OUTPUT の末尾の表から読みます。表は OUTPUT の最後に書かれるので、公式版などが読む決まった行（26・29〜40・65 行目）は動きません。1 にしても予測の数字が変わらないこと（同じ種で同じ値）を、テストで確かめてから使います。
- だめなら第二案（RATIO）: 記録にある値（混合と客観の真ん中・AI の倍率・補正の係数・スポット）から割合で分け、合わない分は `other_yen` に入れます。

| 項目 | 中身 |
|---|---|
| 書く操作 | 予測の保存（`Forecast.js` の `appForecastRunSave_`）。同じ控えで 12 行を足します |
| 見る画面 | 予測の「根拠」（前の回とくらべて、どの層で変わったか）、学び（もし入れていなかったらの比べの材料）、物差しを人と AI の層まで広げるとき |
| 増え方 | 12 行 × 予測の回数。目安: 1 計画 年 50 回で 600 行・約 9,000 セル |
| 残し方 | 消しません。年度の控えに入ります |
| 見られる人 | 計画を見られる人（層ごとの合計だけ。人ごとの内訳は今までどおり `SUBJECTIVE_IMPACT_HISTORY` から、予算策定担当以上だけ） |
| 移行 | 過去の回は作りません（元の表は残っているので、要るときに後から作れます） |
| テスト | 6 つの層を足すと最後の値に一致する（月ごと）／LMDI を 1 にしても予測の数字が同じ／締まった月の行に印が付く／二重にならない |

### 3-4 当たりの記録 `HIT_RECORDS`（決定 15・17 の土台）

- 動きの変化: 予測し直しても予算が真ん中に戻らなくなります。保存される OUTPUT の中身（入力のハッシュ）も変わります。
- 作った後の直し（2026-10-09。確かめで見つけたもの）:
  - 確率で選ぶ予算の「過去の平均の形」は、12 か月とも締まった年度だけを数えます（今日の境目・取り込んだときの境目・`SALES_INPUT` の締まりの印のいちばん厳しい読み方）。来年度の計画を今の年度の途中に作ると、A-2 は今の年度を途中まで（残りの月は 0 円で）取り込むため、前はその年度も数えて割り振りが前半に寄っていました。2 年に足りなければ予測の月の形です（今までどおり）。
  - 移行がバックアップを待っている間も、もうある版 10 の記録の表には足します（表ごとに、表があって見出しが今の列なら書く）。待つのは予算の下書きだけです。前は版の印だけを見て、その間の保存の記録（入力の自信など）が失われていました。

### 4-2 公式版の列（`PLAN_VERSIONS` に足す。決定 28）

公式版を出したときの「届く見込み」と前提を残します。出した後は変えません（公式版の決まりどおり）。

- 書く操作: 公式版を出す（`Versions.js` の `appVersionSubmit_`）。
- 見る画面: 公式版の一覧と承認（承認する人が見込みと前提を見て判断）、期中の「承認したとき → 今」の見込みの並べ、年度末の採点。

- テスト: 出したときに列が入る／出した後に変わらない／前の版が読める／試しの印が画面に出る／本番の版の `center` が出したときの見せる中心と同じ。

- 補足の欄には「先方の方の個人名や患者さんの情報は書かない」とカーソルで案内します。機械では見分けられないので、案内だけです（法的な判断はしていません）。

### 5-2 見られる人（決定 19・20）

| 人 | 見られるもの |
|---|---|
| 送った本人 | 自分の情報のすべて（状態と結果）。決定 18 により、自分の当たりも |
| そのメーカーの予算策定担当以上（メーカー単位の担当を含む） | そのメーカーの情報のすべてと、送った人の名前 |
| ほかの人 | 何も見えない。件数も出さない |

- 送れるのは社内の全員で、どのメーカーについても送れます（決定 19）。
- 見せない人には、サーバーの応答そのものから外します（予測の画面と同じ作り）。
- 社内に公開する（`DOMAIN`）までは、所有者だけが送れます。

### 5-3 仕分けの状態

| 状態 | 意味 | 付ける人 |
|---|---|---|
| 新着 | まだ見ていない | 送ったとき |
| 予測に入れた | 入力の表に書き写した（5-4） | 予算策定担当以上 |
| 根拠に残す | 予測は変えないが、判断の材料に残す | 予算策定担当以上 |
| 重複 | 同じ話の別の情報がある（その番号につなぐ） | 予算策定担当以上 |
| 使わない | 理由を一言 | 予算策定担当以上 |
| 取り下げ | 送った人が取り下げた | 送った本人（予測に入れる前だけ） |

- どの状態でも行は消しません。

### 5-4 書き写しのつなぎ（決定 21）

- 予測に効くのは、予算策定担当が下書きを確かめて「入力を保存」したときだけです。情報が自動で予測を動かすことはありません。
- 書き写した行の担当者の欄は、**予算策定担当の名前に情報の番号を添えた形**にします（決定 21 (a)）。区切りの書き方は版 12 の前に決めます。
- つなぎは 3 か所に残します: 入力の記録（`INPUT_LOG.signal_id`）・情報の表（`transcribed_*`）・当たりの記録（`source_kind` = SIGNAL）。
- 注: 旧来の計算は、担当者の欄の名前ごとに信頼度を引き、見解は人ごとに一番新しい月の 1 行だけを効かせます。名前に番号を添えると、その行は「別の人」として扱われます（信頼度は既定の 1・見解は情報ごとに 1 行が効く）。これを良しとするかを版 12 の前に確かめていただきます。

### 5-5 締まった後の結果

- 情報の時期の終わりの月が締まった後（月末から 5 日たって取り込んだ月）だけ付けられます。
- 予算策定担当が 5 つから選びます: 起きた／一部／起きなかった／時期がずれた／分からない。
- アプリは締まった月の実績から目安を出すだけです（`outcome_hint_json`）。
- 1 件は 1 回だけ数えます（月ごとに数えません）。重複の情報は元の 1 件だけを数えます。

### 5-6 控えの印を分ける（決定 23）

- `APP_TABLES.SIGNALS` に「控えの組」の印を付け、この表への書き込みは、全体の印（`APP_DATA_GEN`）ではなく情報の表の印だけを変えます（`Store.js` の書き込みと、記録つきの操作の終わり `appAudited_` の両方）。
- 情報の画面は、情報の表の印で控えます。ほかの画面の控えは、情報を送っても古くなりません。
- ホームのよみの「新しい情報が N 件」は、ホームの控えの外で数えます（ホームの控えを古くしないため）。
- テスト: 情報を送ってもホーム・予測・分析の控えが使われ続ける／情報の画面は送った直後に新しい件数を出す。

### 5-7 年度と締め

- 情報の表には `plan_id` が無いので、今の年度の控えには入りません。`YearSnapshot.js` に「`fy` の列がある表は、その年度の行を入れる」を足します。
- 締めた年度の情報の行は書けないようにします（仕分けと結果も）。そのため、年度を締める前に、その年度の情報の結果を付け終える必要があります。

| 項目 | 中身 |
|---|---|
| 増え方 | 1 件 1 行・33 列。目安: 社内で月 50 件なら年 600 行・約 2 万セル |
| 残し方 | 消しません。年度の控えに入ります |
| 移行 | 空で作ります |
| テスト | 見られる人の 3 つの場合（`app-plan-privacy` と同じ作り）／メーカー単位の担当は範囲外を受け取らない／ほかの人の応答に件数も入らない／中身の列は変えられない／取り下げ・重複・使わないで行が残る／締まる前は結果を付けられない／年度の控えに入る |

## 9. 確かめていただくこと

### 版 10 を始める前

1. 表の一覧と列（3-1〜3-9）。

10. 年度の最後の四半期の当たりを、年度を締める条件に足すか（おすすめ: 足す）。

### 版 12 を始める前

1. 情報の表の列と 9 つの種類、仕分けの 6 つの状態、結果の 5 つ。
