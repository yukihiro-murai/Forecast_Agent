## 完成形

1. 社内のメンバーが、アプリの画面だけで 1 年を回せる。
   - 計画を作る → 取り込み（A-2・B-1）→ AI 調査（A-4）→ 予測 → 入力 → 予算 → 公式版を出す → 承認

4. 利用者向けの使い方と管理者向けの運用手順（復元・権限・年度の切り替え）が、`app/README.md` の 1 か所にある。

## 段階

各段のやり方は同じです。
1. テストを足す。
2. テストを全部通す。
3. commit・push する。
4. `clasp status` → `clasp push -f` → `clasp deploy -i <ID>`（同じ URL）で公開する。
5. 公開した版の中身が Git と同じかを確かめる。

**公開範囲・権限（scope）・保存先を変えるものは、必ず村井さんの明示の承認を得てから行います。**

### P0 実データでの確認（村井さんが操作する。エージェントは見つかった不具合を直す）
- 「今の状態」の表で未確認の 6 項目を、村井さんに実データで試してもらいます。手順の一覧を渡してください。
- 不具合は、再現するテストを足してから直します。
- 完了の条件: 6 項目がすべて「確認済み」になる。

### P1 公開前の点検（エージェント）
1. **権限の点検**（`tests/` に足す）
   - 閲覧だけの社内の人: 書き込み・実行の API がすべて拒否され、画面に書き込みのボタンが出ない。
   - 予算策定担当（クライアントを絞った人）: 範囲外の計画に書けない。
   - 社外の人・メールが取れない人: 何もできない（fail-closed）。
   - 公開する関数は `doGet`・`api*`・`trigger*` だけ（契約テストを広げる）。
2. **複数の人が同時に使うときの点検**
   - 2 人が同じ計画を同時に保存したとき: 入力のハッシュの食い違いで後の人が止まり、データが壊れないこと。
   - 処理の実行中にほかの人が実行を頼んだとき: 画面の言い方と、待つ・やり直す流れ。
   - 待ち行列にする（順番に動かす）かどうかを提案します。採るかは村井さんが決めます。
3. **上限の見積もり**
   - トリガーの実行時間の 1 日の上限と、同時実行の上限。
   - 「計画の数 × 月の実行回数」で足りるかを、RUN ログの実測から計算して記録します。
4. **組み立ての段（100〜120 秒）を短くする調べ**
   - どこに時間がかかっているかを RUN ログと段ごとの時間で調べます。
   - 計算・保存・予測の判定は変えません。候補を挙げて村井さんに提案します。
- 完了の条件: 点検のテストが通る。見積もりと提案が `DESIGN_evolution_JA.md` に記録されている。

2. **年度の締め**

   - 次の年度の計画は「計画を作る」で作ります。
3. **定期の自動実行**
