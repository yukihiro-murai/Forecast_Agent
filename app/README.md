## 旧ブックの取り込み（段階2）

「旧ブックから移す」の画面（所有者だけ）で、旧ブック「クライアント別売上予測」の URL を入れて使います。

1. **試しに読む** — データ本体には書きません。旧ブックの各シートについて、次の2点を確かめて結果を出します。
   - 保存の形（`ENG_*`）にして戻すと、値・型・数式・表示形式・大きさが元と同じになるか
   - 計算用ブックに組み立てて読み戻すと、元と同じ値になるか（自動変換で変わるセルは書き方を変えて直す）
2. **取り込む** — 試しのときと旧ブックの内容が同じ（内容のハッシュが一致）ときだけ、計画1つ分の `ENG_*` を入れ替えます。前回と同じ内容なら何も書きません。

どちらも裏で動く処理です（`Jobs.js`。1 回だけのトリガーで最後まで動かし、画面は数秒ごとに状態を尋ねる）。画面と 1 分を超えてつながったままにすると通信が切れる（HTTP 503）ことがあるためです。画面を閉じても処理は続き、開き直すと結果を待ちます。

旧ブックは読むだけで、何も変えません。表の列は旧来のシートの見出しと同じで、`Schema.js` の `APP_ENGINE_SHEETS` にあります（`app/tests/app-migration.test.mjs` が `Forecast_Agent.js` の定義と照合します）。版を上げて表を足したときは、公開した後の最初の操作（画面を開く・裏の処理を含む）で自動で作ります（`appAutoEnsureTables_`。作った表は実行ログに残る）。「状態」の「足りない表を作る」でも作れます。

## 旧来の計算と、計算の一致の確認（段階2-2）

- 旧来の計算（ルートの `Forecast_Agent.js`）と旧来の Web アプリ（`Forecast_WebApp.js`）は、`app/src/LegacyEngine.js` にそのまま関数で包んで入れます（自動生成。中身は1文字も変えない）。**どちらかを変えたら作り直してください**（`app/tests/app-engine.test.mjs` が古いと失敗します）。

  ```bash
  node app/tools/build-engine.mjs
  ```

- 計算は計算用ブックの上で動かします（`Engine.js`）。そのとき次を差し替えます。
  - 開いているスプレッドシート → 計算用ブック
  - 「今」→ 実行の時刻に固定
  - 乱数 → 種で固定
  - 旧来の計算が作る ID → 種から決まるもの
  - 画面・外部への通信 → 止める
- 「旧ブックから移す」の「計算の一致を確かめる」（所有者だけ、`Parity.js`）は、次の順に動きます。
  1. 旧ブックのシートをそのまま写した計算用ブックで予測を実行し、計算後の全シートの控えを取る
  2. データ本体から組み立てた計算用ブックで、同じ種・同じ時刻で予測を実行する
  3. 計算後の全シートを、1 の控えと比べる
- データ本体にも旧ブックにも書きません。1 回の実行の上限（6 分）に収まるよう、2 つの処理に分けて続けて動かします。

## 新アプリでの予測の実行（段階2-2b）

- 「予測」の画面の「予測を実行」から動かします。予算策定担当（その計画のクライアントの担当でもよい）以上の人が使えます。
- 次の2つの処理が続けて動きます（`Forecast.js`）。
  1. 計算: データ本体から計算用ブックを組み立て、旧来の予測（A-9）を動かし、書き換わったシートの控えを取る
  2. 保存: 計算の間にデータ本体が変わっていないことを確かめてから、控えをデータ本体へ戻す
- 種（乱数）は実行の ID、「今」は実行を始めた時刻です。結果は `FORECAST_RUNS`（1回1行）と `FORECAST_MONTHLY`（月ごと）に残ります。
- 旧来の計算が入力の確認（極端な入力値など）を求めたときは、何も保存せずに画面で内容を見せ、続けるときだけもう一度動かします。
- 履歴の表（`FORECAST_SNAPSHOT` など）は、足された行だけを書きます。
- 旧ブックは変わりません。並行運用の間に旧ブックを取り込み直すと、計算用の表は旧ブックの内容に戻ります（予測の記録は残ります）。

## 計画の画面（段階2-3）

「予測」の画面のタブで、旧来の Web アプリと同じ中身を見て、保存・実行します（`Plan.js`）。見るのは社内全員です。

| タブ | 見るもの | 保存・実行（役割） |
|---|---|---|
| 予測と予算 | 最新の予測、月ごとの予算（採用予測・上乗せ・最終予算） | 予測の実行・予算の保存（予算策定担当） |
| 入力 | 製品・クライアント全体・見解・スポット案件 | 入力の保存（予算策定担当。種類ごとに全部書き換える。旧来と同じ） |
| 検証 | 精度の指標、月ごとの予測と実績、学習インサイト | B-1 の取り込み（管理者）、B-2〜B-5 の実行・インサイトの記入の保存（予算策定担当） |
| 四半期レビュー | 提案と承認、これまでのレビュー | C-1 の実行（予算策定担当）、承認の保存・C-3 の適用（承認者） |
| 進み | 手順ごとの状態、この計画の最近の操作、担当者 | A-2 の取り込み・担当者の保存（管理者）、A-3 の実行（予算策定担当） |

- 見る: データ本体から読むだけのブックを組み立て、旧来の `webGetBootstrap_` をそのまま動かします（計算用ブックは使わない）。入力が同じ間は 6 時間覚えておきます。旧来が書く数式は OUTPUT の予算の列（`=SUM(..)` と `=H+I`）だけなので、その 2 つだけを計算します。
- 保存: 使うシートだけを計算用ブックに組み立て、旧来の `webSave*` をそのまま動かし、変わったシートをデータ本体へ戻します（1 つの裏の処理）。画面を開いた後にほかの人の操作でデータが変わっていたら止めます。
- 実行: 予測と同じく、組み立て → 計算 → 保存の 3 つの裏の処理で戻します（組み立ては 1 回の上限に収まらなければ何回かに分かれる）。計算用ブックは処理の印（`APP_SCRATCH_OWNER`）で、組み立てたままかを確かめます。
- 書き込みは保存の控え（`Journal.js`）を置いてから行います。書き終えた後の表の中身をシステムのフォルダのファイルに置き、書き終えたら消します。途中で止まったら（時間切れ・Google 側のエラー）、次の書き込みの前か、画面の「保存の続きを書く」（`SYSTEM.RECOVER`）で控えのとおりに書き直します。止まっている間は、計画の画面の中身を出しません。
- 「=」（と、「+」「-」の後に英字や括弧が続くもの）で始まる入力は受け付けません。計算用ブックは所有者の権限で動くので、外部を読む数式（IMPORTXML など）を動かさないためです。
- 記録は `PLAN_ACTIONS`（1 回 1 行）と操作の記録（保存した中身も残す）。旧来の操作の記録（`webAudited_`）と管理者の判定（`webActor_`）だけは新アプリが行うので、包んだ中で差し替えています。
- 「旧ブックから移す」の「画面の中身を確かめる」（所有者）で、計算用ブックで読んだものとデータ本体から読んだものが同じかを確かめられます。
- 売上・検証用実績の取り込み（A-2・B-1）の元は「設定」の「ZAC の実績のスプレッドシート」（URL を入れると、開けるスプレッドシートかを確かめて ID で持つ）。旧アプリの Admin Hub の「実績ソース」と同じものを入れる。未設定なら取り込まない（旧来のコードにある既定のファイルには頼らない）。
- 担当者（A-1 のうち担当者だけ）は CONFIG!B4 と計画の表（PLANS）の両方に書く。クライアントと年度は計画で決まるので、この画面では変えない。
- まだ旧アプリで行うもの: AI 調査（A-4）と Vertex のアシスト（Google Cloud を使う権限を新アプリに足し、所有者の承認が要る）。新しい計画（別のクライアント・年度）は、今は旧ブックの取り込みで作る。

社外の人・メールが取れない人には何も許しません。付与は消さずに無効にし（期間つき）、変更はすべて操作の記録に変更前後が残ります。

## コードの約束

- 公開する関数（ブラウザから `google.script.run` で呼べる関数）は `Api.js` の `doGet`・`api*`・`trigger*` だけ。どれも本体は `return api_(...)` だけにし、本人確認 → 役割 → 記録つき実行 → エラーの記録 を必ず通す。それ以外の関数は名前の末尾を `_` にする。
- 書き込みは開始を記録できなければ実行しない（fail-closed）。記録はハッシュの鎖でつなぎ、「状態」の画面で改ざんを点検できる。
- 表の列は `Schema.js` だけで決める。データ本体の 1 行目が定義と違えば書き込みを止める。列を変えるときは版を上げて移行する。
- `Assets.js` は自動生成（`cd ../assets/characters/src && python3 build.py`）。手で編集しない。
