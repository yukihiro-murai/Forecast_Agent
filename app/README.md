### 名前と技術 ID（2026-10-06 に Trends2Targets へ統一）

- 改名したもの（どれも同じ ID のまま）: GitHub のリポジトリ（`Forecast_Agent` → `Trends2Targets`。旧 URL は GitHub が転送）、Mac のフォルダ（`~/Documents/GAS/Trends2Targets`。旧パス `Forecast_Agent` は互換の symlink）、Apps Script（「売上予測アプリ」→「Trends2Targets」）、Drive のフォルダ・データ本体・ログ・計算用ブック（「売上予測アプリ …」→「Trends2Targets …」）。
- 変えないもの: スクリプト・ファイル・デプロイの ID、Script Properties のキー、旧来の計算のファイル名 `Forecast_Agent.js`、表とシートの名前、過去の記録の文面。ファイルは ID で開くので、名前を変えても動きは変わりません。
- 名前で探すのはバックアップの世代と月次の写しだけです。前の名前（`APP_FILES_LEGACY`）のものも数えます。
- もう一台の Mac の追従: `git remote set-url origin git@github.com:yukihiro-murai/Trends2Targets.git` → `git fetch` → 変更が無いのを確かめてから GAS の親フォルダで `mv Forecast_Agent Trends2Targets && ln -s Trends2Targets Forecast_Agent`（`Trends2Targets` が既にあれば止める）。

メンバーにはどのファイルも共有しません。メンバーはアプリ画面だけを使い、誰が何をできるかはアプリが判定します。データ本体は直接編集しないでください（画面からの変更だけが記録に残ります）。

## 計算用の表（ENG_*）

旧来の計算が読み書きするシートは、データ本体の `ENG_*` の表に計画ごとに持ちます（`Legacy.js` が相互変換。値は型ごと、表示形式は列ごとの並びで持ち、計算用ブックに保存したときと同じ状態を組み立て直せる）。表の列は旧来のシートの見出しと同じで、`Schema.js` の `APP_ENGINE_SHEETS` にあります（`app/tests/app-codec.test.mjs` が `Forecast_Agent.js` の定義と照合します）。

時間のかかる処理は裏で動かします（`Jobs.js`。1 回だけのトリガーで最後まで動かし、画面は数秒ごとに状態を尋ねる）。画面と 1 分を超えてつながったままにすると通信が切れる（HTTP 503）ことがあるためです。画面を閉じても処理は続き、開き直すと結果を待ちます。

版を上げて表を足したときは、公開した後の最初の操作（画面を開く・裏の処理を含む）で自動で作ります（`appAutoEnsureTables_`。作った表は実行ログに残る）。「状態」の「足りない表を作る」でも作れます。使わなくなった表（`APP_RETIRED_TABLES`。今は旧ブックからの取り込みの記録 `IMPORT_BATCHES`）は作らず、前からあるシートは消さずに隠します。

計画は「メーカー」の「計画を作る」で作ります（旧来の A-1 初期セットアップを計算用ブックで動かして保存。2026-10-05 に旧ブックからの取り込みを外した）。

## 旧来の計算（段階2-2）

- 旧来の計算（ルートの `Forecast_Agent.js`）と旧来の Web アプリ（`Forecast_WebApp.js`）は、`app/src/LegacyEngine.js` にそのまま関数で包んで入れます（自動生成。中身は1文字も変えない）。**どちらかを変えたら作り直してください**（`app/tests/app-engine.test.mjs` が古いと失敗します）。

  ```bash
  node app/tools/build-engine.mjs
  ```

- 計算は計算用ブックの上で動かします（`Engine.js`）。そのとき次を差し替えます。
  - 開いているスプレッドシート → 計算用ブック
  - 「今」→ 実行の時刻に固定
  - 乱数 → 種で固定
  - 旧来の計算が作る ID → 種から決まるもの
  - 画面・外部への通信 → 止める

## 新アプリでの予測の実行（段階2-2b）

- 「予測」の画面の「予測を実行」から動かします。予算策定担当（その計画のクライアントの担当でもよい）以上の人が使えます。
- 次の2つの処理が続けて動きます（`Forecast.js`）。
  1. 計算: データ本体から計算用ブックを組み立て、旧来の予測（A-9）を動かし、書き換わったシートの控えを取る
  2. 保存: 計算の間にデータ本体が変わっていないことを確かめてから、控えをデータ本体へ戻す
- 種（乱数）は実行の ID、「今」は実行を始めた時刻です。結果は `FORECAST_RUNS`（1回1行）と `FORECAST_MONTHLY`（月ごと）に残ります。
- 旧来の計算が入力の確認（極端な入力値など）を求めたときは、何も保存せずに画面で内容を見せ、続けるときだけもう一度動かします。
- 履歴の表（`FORECAST_SNAPSHOT` など）は、足された行だけを書きます。

## 計画の画面（段階2-3）

「予測」の画面のタブで、旧来の Web アプリと同じ中身を見て、保存・実行します（`Plan.js`）。見るのは社内全員です。

| タブ | 見るもの | 保存・実行（役割） |
|---|---|---|
| 予測と予算 | 最新の予測、月ごとの予算（採用予測・上乗せ・最終予算） | 予測の実行・予算の保存（予算策定担当） |
| 入力 | 製品・クライアント全体・見解・スポット案件 | 入力の保存（予算策定担当。種類ごとに全部書き換える。旧来と同じ） |
| 検証 | 精度の指標、月ごとの予測と実績、学習インサイト | B-1 の取り込み（管理者）、B-2〜B-5 の実行・インサイトの記入の保存（予算策定担当） |
| 四半期レビュー | 提案と承認、これまでのレビュー | C-1 の実行（予算策定担当）、承認の保存・C-3 の適用（承認者） |
| 進み | 手順ごとの状態、この計画の最近の操作、担当者 | A-2 の取り込み・担当者の保存（管理者）、A-3 の実行（予算策定担当） |

- 見る: データ本体から読むだけのブックを組み立て、旧来の `webGetBootstrap_` をそのまま動かします（計算用ブックは使わない）。入力が同じ間は 6 時間覚えておきます。旧来が書く数式は OUTPUT の予算の列（`=SUM(..)` と `=H+I`）だけなので、その 2 つだけを計算します。
- 保存: 使うシートだけを計算用ブックに組み立て、旧来の `webSave*` をそのまま動かし、変わったシートをデータ本体へ戻します（1 つの裏の処理）。画面を開いた後にほかの人の操作でデータが変わっていたら止めます。
- 実行: 予測と同じく、組み立て → 計算 → 保存の 3 つの裏の処理で戻します（組み立ては 1 回の上限に収まらなければ何回かに分かれる）。計算用ブックは処理の印（`APP_SCRATCH_OWNER`）で、組み立てたままかを確かめます。
- 書き込みは保存の控え（`Journal.js`）を置いてから行います。書き終えた後の表の中身をシステムのフォルダのファイルに置き、書き終えたら消します。途中で止まったら（時間切れ・Google 側のエラー）、次の書き込みの前か、画面の「保存の続きを書く」（`SYSTEM.RECOVER`）で控えのとおりに書き直します。止まっている間は、計画の画面の中身を出しません。
- 「=」（と、「+」「-」の後に英字や括弧が続くもの）で始まる入力は受け付けません。計算用ブックは所有者の権限で動くので、外部を読む数式（IMPORTXML など）を動かさないためです。
- 記録は `PLAN_ACTIONS`（1 回 1 行）と操作の記録（保存した中身も残す）。旧来の操作の記録（`webAudited_`）と管理者の判定（`webActor_`）だけは新アプリが行うので、包んだ中で差し替えています。
- 売上・検証用実績の取り込み（A-2・B-1）の元は「設定」の「ZAC の実績のスプレッドシート」（URL を入れると、開けるスプレッドシートかを確かめて ID で持つ）。未設定なら取り込まない（旧来のコードにある既定のファイルには頼らない）。
- 担当者（A-1 のうち担当者だけ）は CONFIG!B4 と計画の表（PLANS）の両方に書く。クライアントと年度は計画で決まるので、この画面では変えない。

## 毎日の手入れ・バックアップ・異常の通知（v0.23.0・@48 公開済み）

- バックアップは毎日の定時実行でデータ本体の複製を作り、バックアップのフォルダに新しい 14 世代を残します。それより古い複製はアーカイブのフォルダへ移します（名前・ID・中身はそのまま。ゴミ箱には送りません）。アーカイブのフォルダが見つからないときは複製を作る前に止まります。
- 定時実行で異常があったとき（バックアップの失敗・手入れの失敗・監査の鎖の切れ・終わりの無い開始の記録・書きかけの控え・24 時間のエラー）は、所有者と「全体・管理者」の役割が有効な人へメールで知らせます（`Notifications.js`。1 日・同じ異常の組み合わせごとに 1 通まで。本文は異常の種類の名前だけで、名前・数字・ID・メールアドレスは入れない）。
- 通知は**定時実行（`triggerDailyBackup`）の中だけ**で送ります。画面や手動の「今すぐバックアップ」「今すぐ手入れ」からは送りません。
- **2026-10-06 村井さんの判断で、通知メールの許可は出していません**（異常はホームのよみのセリフと「記録と状態」の画面で確認します）。許可が無い間は送信が失敗として記録されるだけで、定時処理の結果は変わらない設計です。次の手順は、将来メールを使う場合のものです。なお `appAuthorizeMaintenance_` は名前が `_` で終わるため、エディタの実行の一覧に出ません。使う場合は所有者だけの入口（`apiAuthorizeAi` と同じ形）を足す必要があります（要承認）。
- メールを送る権限（scope: `script.send_mail`）を足したので、**所有者が 1 回、許可を確認する操作が要ります**。Apps Script エディタで関数 `appAuthorizeMaintenance_` を選んで実行し、Google の許可の画面でメールを送る権限を認めてください（この関数はメールを送りません。許可があることを確かめるだけです）。確認するまで通知は届きません（実際に届くかはまだ確かめていません）。
- なお、メールの送信と「送った」控えの記録は別の操作です。送信または保存場所の障害の途中では、重複して届いたり・届かなかったりする可能性があり、厳密に 1 回だけ届くことは保証しません。

## 年度の締め（v0.24.0・@49 公開済み）

- 管理者が「記録と状態」の「状態」の「年度の締め」で、今年度より前の年度を選び、「内容を確認」で計画の数・行の数・控えの大きさを確かめてから「年度を締める」を押します（裏の処理として動き、終わると状態が新しくなります）。今年度や未来の年度は選べません。
- 締めると、その年度の計画と関係する表の行を写した年度の控え（JSON・上限 8MB）をアーカイブのフォルダへ 1 ファイル残し、読み直して一致を確かめてから、年度を閉じた記録を 1 行だけ足します。**元の行は動かさず・消さず・隠さず**、その年度は全部の書き込み経路で読み取り専用になります（画面には「凍結」の印が出ます）。開き直す操作はありません。
- 締められるには、その年度の全部の計画に承認済みの公式版が要ります。保存の控え・承認待ち・動いている処理があると止まります。自動では締めません。実際の年度を締める操作はまだしていません。

## 市場の動きの自動収集（A-4 AI 調査を週 1 回。2026-10-06 村井さん承認「週1回自動」・未公開）

- **計画ごとに週 1 回**: 進行中・今年度か来年度・年度を締めていない計画のうち、最後の A-4 から 7 日を過ぎた（一度も無い）計画を、古い順に集め直します。画面から A-4 を動かした計画は、そこから 7 日たつまで自動では動かしません。A-4 以外の操作（取り込み・予測・学習の反映など）は、今までどおり手で動かします。
- **時間**: 毎日 4 時半ごろ（4:15〜4:45 のどこか）の定時実行（`triggerAutoResearch`、所有者として動く）が、いちばん古い計画を 1 つ選び、画面から始めるのと同じ裏の処理で A-4 を動かします（`AutoResearch.js`）。権限の確かめと監査の記録は画面から始めたときと同じです。
  - 3 時台の毎日のバックアップと手入れ（`triggerDailyBackup`）とはロックを取り合うので、時間を分けています。始めてよいのは 4:00〜7:00 の間だけです。
  - 毎日のバックアップのトリガーがあるときは、その日の手入れが終わって 5 分たつまで始めません（手入れの控え `APP_HOUSEKEEPING` の時刻で見ます）。手入れが遅れた日は、その晩は見送ります。
  - 自動で始めた A-4 が終わったら（成功でも失敗でも）、7 時より前なら次に古い計画を続けて始めます（1 晩 12 計画まで）。ほかの処理が動いている・待っているときは何もしません。
- CONFIG の `AI_RESEARCH_ENABLED` が 0・Vertex の設定が無い・A-2 売上の取り込みが済んでいない計画は飛ばして、同じ回で次の計画を探します（1 回に 20 計画まで）。自動で失敗した・飛ばした・権限が足りなかった計画は 3 日あけてから試します。
- トリガーは毎日の手入れと、所有者が画面を開いたとき（確かめるのは 1 日 1 回）に、無ければ作ります（トリガーの上限 20 に余裕が無ければ作りません）。前の版で作った 1 時ごろのトリガーは、新しい版で最初に確かめたときに 1 回だけ消して 4 時半ごろで作り直します（確かめた控え `APP_AUTO_RESEARCH_CHECKED` の時刻の版で見ます）。
- **止めるとき**: スクリプトのプロパティ `AUTO_RESEARCH_ENABLED` を `false` にします（トリガーは残っても何もしません。止めている間は新しく作りません）。プロパティを消すと元に戻ります（トリガーが無ければ、次の確かめで作ります）。
- 毎回の結果は実行ログ（種類 `AUTO.RESEARCH`）に残り、管理者のホームの仕組みの状態（`system.autoResearch`）に、時間・最後の回・最後に始めた計画・結果・7 日の失敗の数・古いままの計画が、画面の名前（`statusLabel`・`reasonLabel`）つきで出ます。状態の控え（`APP_AUTO_RESEARCH`）は約 8000 バイトより小さく保ちます（失敗の理由は要点 40 字まで。失敗の文そのものは実行ログに残ります）。

見送った・飛ばした理由（`reason`）の意味:

| 印 | 意味 | すること |
|---|---|---|
| `DISABLED` | 止めるスイッチが切ってある | 動かすなら `AUTO_RESEARCH_ENABLED` を消す |
| `BEFORE_HOURS` / `AFTER_HOURS` | 4 時より前・7 時を過ぎた | なし（次の晩に続く） |
| `MAINTENANCE_PENDING` | 今日の毎日の手入れがまだ終わっていない | 続くときは「状態」で手入れの結果を見る |
| `BUSY` | ほかの処理が動いている・待っている | なし |
| `NIGHT_LIMIT` | 1 晩に始める上限（12 計画）に達した | なし（次の晩に続く） |
| `NO_STALE_PLAN` | 7 日を過ぎた計画が無い（試してから 3 日たっていないものは除く） | なし |
| `NOT_READY` | 準備ができていない（`AI_DISABLED` AI 調査が無効・`VERTEX_CONFIG` Vertex の設定が足りない・`NO_SALES_DATA` A-2 が済んでいない・`NO_SETUP` CONFIG が無い） | 計画の設定を直すか、そのままにする（3 日ごとに確かめ直す） |
| `DENIED` | 頼んだ人（所有者）に、その計画の A-4 を動かす権限が無い | 役割を確かめる |
| `START_FAILED` / `FAILED` / `STALLED` | 始められなかった・A-4 が失敗した・途中で止まった | 実行ログとエラーログで理由を見る（7 日の失敗の数に入る） |

## 所有者の操作（エディタから）

管理の画面（設定・メンバーと役割・表示名・記録と状態・年度の締め・計画の作成）は画面から外します（2026-10-06 村井さん決定）。これらの操作は、所有者が Apps Script のエディタから `apiOwnerTask` で行います（`OwnerTask.js`）。エディタから実行する関数には引数を渡せないので、頼む操作はスクリプト プロパティ `OWNER_TASK` に JSON で書きます。

1. Apps Script のエディタで「Trends2Targets」のプロジェクトを開きます。
2. 左の「プロジェクトの設定」（歯車）を開き、いちばん下の「スクリプト プロパティ」で「スクリプト プロパティを編集」→「スクリプト プロパティを追加」を押します。
3. プロパティに `OWNER_TASK`、値に下の表の JSON を 1 行で入れ、「スクリプト プロパティを保存」を押します（すでにあるときは値だけ書き換えます）。
4. 左の「エディタ」で `Api.gs` を開き、上の関数の一覧から `apiOwnerTask` を選んで「実行」を押します。
5. 下の「実行ログ」に結果の全部が出ます。同じ結果（大きいときは要約）がスクリプト プロパティ `OWNER_TASK_RESULT` に入ります（「プロジェクトの設定」を開き直すと見えます）。`"ok": true` ならうまくいっています。
6. うまくいくと `OWNER_TASK` は消えます（同じ操作を 2 度動かさないため）。失敗したときは `"ok": false` と理由（`error`）が入り、`OWNER_TASK` は残るので、直してもう一度実行します。

- 中で使う関数・権限の判定・入力の確かめは、画面の操作と同じです。書く操作は画面と同じ操作の名前（`SETTING.SAVE`・`ROLE.GRANT` など）で操作の記録に残り、理由の欄に「OWNER_TASK（エディタから）」と入ります。所有者のほかの人が `apiOwnerTask` を動かしても断られます（断ったことは記録に残ります）。
- 時間のかかる操作（`createPlan`・`setPeople`・`yearClose`・`poolApply`）は、画面と同じく裏の処理として始まり、結果に `jobId` が出ます。1〜2 分おいて `{"action":"jobStatus"}` を実行すると結果が分かります（`jobId` を省くと、最後に始めた処理）。
- `roleId`・`rowVersion`・`clientId` は `listDirectory`、`planId` は `listPlans`、ZAC の名前は `planCandidates` の結果から写します。
- 年度の締めは、必ず `yearPreview` で `"canClose": true` を確かめ、出た `inputHash`（64 桁）をそのまま `yearClose` に渡します。確認の後に年度の中身が変わっていれば、締めずに止まります。

| 操作 | すること | `OWNER_TASK` の例 |
|---|---|---|
| `listDirectory` | メンバー・有効な役割・メーカー（ID と表示名）を見る | `{"action":"listDirectory"}` |
| `saveMember` | メンバーを登録する・直す（社内のメールだけ） | `{"action":"saveMember","email":"name@bigm2y.com","displayName":"山田 太郎","department":"営業部"}` |
| `grantRole` | 役割を付ける（`PLANNER`・`APPROVER`・`ADMIN`。`scopeType` は `ALL` か、予算策定担当だけ `CLIENT`） | `{"action":"grantRole","email":"name@bigm2y.com","role":"PLANNER","scopeType":"CLIENT","clientId":"CL-…"}` |
| `revokeRole` | 役割を外す（行は残して無効にする） | `{"action":"revokeRole","roleId":"RL-…","rowVersion":1}` |
| `saveClientName` | メーカーの画面の名前を決める（空にすると自動の名前に戻す） | `{"action":"saveClientName","clientId":"CL-…","displayName":"アストラゼネカ","rowVersion":""}` |
| `listSettings` | 業務の設定を見る | `{"action":"listSettings"}` |
| `saveSetting` | ZAC の実績のスプレッドシートを決める | `{"action":"saveSetting","key":"source.zac_spreadsheet","value":"https://docs.google.com/spreadsheets/d/…/edit"}` |
| `listPlans` | 計画の一覧（`planId`）を見る | `{"action":"listPlans"}` |
| `planCandidates` | 計画を作れるメーカーの候補（ZAC の名前）を見る（`"refresh":true` で ZAC を読み直す） | `{"action":"planCandidates"}` |
| `createPlan` | 計画を作る（裏の処理） | `{"action":"createPlan","clientName":"（ZAC の名前）","fy":2027,"peopleCsv":"鷹野,佐藤"}` |
| `setPeople` | 計画の担当者を変える（裏の処理） | `{"action":"setPeople","planId":"PL-…","peopleCsv":"鷹野,佐藤"}` |
| `enableBackup` | 毎日のバックアップを有効にする | `{"action":"enableBackup"}` |
| `runBackup` | 今すぐバックアップを取る | `{"action":"runBackup"}` |
| `runHousekeeping` | 毎日の手入れを今すぐ動かす | `{"action":"runHousekeeping"}` |
| `verifyAudit` | 監査の鎖を全部の月で確かめる | `{"action":"verifyAudit"}` |
| `health` | 状態の要約（問題のある表・監査・バックアップ・手入れ・保存の控え・年度） | `{"action":"health"}` |
| `yearPreview` | 年度を締められるか確かめ、指紋（`inputHash`）を受け取る（何も書かない） | `{"action":"yearPreview","fy":2025}` |
| `yearClose` | 確かめた指紋で年度を締める（裏の処理。元に戻せません） | `{"action":"yearClose","fy":2025,"inputHash":"（yearPreview の inputHash）"}` |

| `listAudit` | ログを見る（`kind` は `AUDIT`・`RUN`・`ERROR`、`month` は `yyyy_MM`、`query` で絞る） | `{"action":"listAudit","kind":"AUDIT","month":"2026_10","query":"ROLE"}` |
| `jobStatus` | 裏の処理の結果を見る | `{"action":"jobStatus"}` |

## 利用者・管理者の運用手順

現在は所有者だけが開けます（MYSELF）。役割の判定はローカルで検証済みですが、社内の複数人での実運用は未確認です。

| 役割 | 画面と操作 |
|---|---|
| 閲覧・情報提供 | ホーム、計画の一覧、予測・予算・根拠・検証・公式版を読む。入力の保存は予算策定担当以上です |
| 予算策定担当 | 入力と予算を保存、予測を実行、公式版として出す、検証と月次学習を更新。クライアント限定の付与では対象の計画だけ書けます |
| 承認者 | 公式版を承認・却下、四半期レビューを判断・適用。既存の役割階層では予算策定担当の操作も含みます |
| 管理者 | 計画作成、設定、売上・実績の取り込み、メンバーと役割、状態、バックアップ、年度締めを管理します |

### 1 年の流れ

1. 管理者が「メーカー」で必要なメーカー・年度・担当者を登録します。年度は4月開始の年で呼びます（FY2026 は2026/04〜2027/03）。
2. 管理者が「進み」で売上取込（A-2）、策定担当が売上加工（A-3）・AI調査（A-4）を実行します。実績の取得元は「設定」で指定したものを使います。
3. 策定担当が入力・予測・予算を整え、「公式版」で提出します。承認者が数字を確認して承認・却下します（自分の提出を承認する扱いは既存ルールに従います）。
4. 実績が締まったら管理者が「検証」で実績取込（B-1）、策定担当が検証更新・指標更新・見立て更新・月次学習（B-2〜B-5）を順に行います。インサイトの記入も保存します。
5. 四半期ごとに提案を作り（C-1）、承認者が判断し、承認した提案を適用します（C-3）。
6. 次年度は新しい計画として作ります。終わった年度を締める場合だけ、管理者が「記録と状態」の「状態」で内容を確認して年度を締めます。現在・未来の年度は締めません。行の移動・凍結解除は行いません。

### 管理者の点検と障害対応

- 「設定」の「メンバー」で社内のメンバーを登録し、役割・対象メーカー・有効期間を確認します。所有者は常に管理者です。付与の無効化と公開範囲の変更は別の操作です。
- 「記録と状態」の「状態」で保存の控え、処理、監査、バックアップ、手入れを確認します。処理中の重複依頼は断られるので、終了後に画面を読み直してから再試行します。古い画面で保存が止まった場合も読み直します。
- 書きかけの保存は、控えの内容を確認して「保存の続きを書く」で復旧します（全体の予算策定担当以上の権限が必要）。凍結記録や控えが壊れている場合は書き込みを止めたままにし、控えを削除して強行しません。
- 日次バックアップは新しい14世代をバックアップフォルダに残し、古い世代と月次の写しはアーカイブに残します。正常な日は通知メールを送りません。通知の権限確認は前の節の `appAuthorizeMaintenance_` を使い、配送確認のために無断のテストメールや意図的な障害を起こしません。

### バックアップからの復元

自動復元の操作は未実装です。まず現在のデータと凍結記録を別の控えとして保全し、復元候補の年度・計画・列・キー・型・数式・書式・凍結記録を読み取りだけで照合します。古いバックアップには年度の締めの記録が無い可能性があるため、丸ごとの差し戻しで締めた年度を開かないようにします。

データ本体の差し替え、保存先の切り替え、行の書き戻しは、具体的な復元設計と村井さんの承認後に行います。凍結記録の表が読めない場合は空で作り直さず、元の記録を戻す方針を先に確認します。元データ・候補ファイルは削除・ゴミ箱送りをしません。

## コードの約束

- 公開する関数（ブラウザから `google.script.run` で呼べる関数）は `Api.js` の `doGet`・`api*`・`trigger*` だけ。どれも本体は `return api_(...)` だけにし、本人確認 → 役割 → 記録つき実行 → エラーの記録 を必ず通す。それ以外の関数は名前の末尾を `_` にする。
- 書き込みは開始を記録できなければ実行しない（fail-closed）。記録はハッシュの鎖でつなぎ、「記録と状態」の画面で改ざんを点検できる。
- 表の列は `Schema.js` だけで決める。データ本体の 1 行目が定義と違えば書き込みを止める。列を変えるときは版を上げて移行する。
- `Assets.js` は自動生成（`cd ../assets/characters/src && python3 build.py`）。手で編集しない。

同じ URL のまま新しい版になります（版の番号 @N を記録に残す）。**裏の処理（トリガー）は公開した版ではなく、最後に push したコードで動きます。** push したら、同じ内容で公開まで続けて行ってください（画面と裏の処理の版がずれないように）。`appsscript.json` を変えたときの `clasp push` は確認待ちになって何も送らないので `-f` を付け、push 後に `clasp clone` で照合します。ルートの `.claspignore` は `app/**` を除いているので、旧来の中央 project には上がりません。
