### 名前と技術 ID（2026-10-06 に Trends2Targets へ統一）

- 変えないもの: スクリプト・ファイル・デプロイの ID、Script Properties のキー、旧来の計算のファイル名 `Forecast_Agent.js`、表とシートの名前、過去の記録の文面。ファイルは ID で開くので、名前を変えても動きは変わりません。
- 名前で探すのはバックアップの世代と月次の写しだけです。前の名前（`APP_FILES_LEGACY`）のものも数えます。
- もう一台の Mac の追従: `git remote set-url origin git@github.com:yukihiro-murai/Trends2Targets.git` → `git fetch` → 変更が無いのを確かめてから GAS の親フォルダで `mv Forecast_Agent Trends2Targets && ln -s Trends2Targets Forecast_Agent`（`Trends2Targets` が既にあれば止める）。

メンバーにはどのファイルも共有しません。メンバーはアプリ画面だけを使い、誰が何をできるかはアプリが判定します。データ本体は直接編集しないでください（画面からの変更だけが記録に残ります）。

## 計算用の表（ENG_*）

旧来の計算が読み書きするシートは、データ本体の `ENG_*` の表に計画ごとに持ちます（`Legacy.js` が相互変換。値は型ごと、表示形式は列ごとの並びで持ち、計算用ブックに保存したときと同じ状態を組み立て直せる）。表の列は旧来のシートの見出しと同じで、`Schema.js` の `APP_ENGINE_SHEETS` にあります（`app/tests/app-codec.test.mjs` が `Forecast_Agent.js` の定義と照合します）。

時間のかかる処理は裏で動かします（`Jobs.js`。1 回だけのトリガーで最後まで動かし、画面は数秒ごとに状態を尋ねる）。画面と 1 分を超えてつながったままにすると通信が切れる（HTTP 503）ことがあるためです。画面を閉じても処理は続き、開き直すと結果を待ちます。

版を上げて表を足したときは、公開した後の最初の操作（画面を開く・裏の処理を含む）で自動で作ります（`appAutoEnsureTables_`。作った表は実行ログに残る）。足りない表は `apiOwnerTask` の `health`（`tables.problems`）で分かり、所有者がエディタから `apiSetup` を実行しても作れます（ある表はそのまま）。使わなくなった表（`APP_RETIRED_TABLES`。今は旧ブックからの取り込みの記録 `IMPORT_BATCHES`）は作らず、前からあるシートは消さずに隠します。

計画は所有者が `apiOwnerTask` の `createPlan` で作ります（画面に計画を作る操作はありません。旧来の A-1 初期セットアップを計算用ブックで動かして保存。2026-10-05 に旧ブックからの取り込みを外した）。

## 旧来の計算（段階2-2）

- 旧来の計算（ルートの `Forecast_Agent.js`）と旧来の Web アプリ（`Forecast_WebApp.js`）は、`app/src/LegacyEngine.js` にそのまま関数で包んで入れます（自動生成。中身は1文字も変えない）。**どちらかを変えたら作り直してください**（`app/tests/app-engine.test.mjs` が古いと失敗します）。

  ```bash
  node app/tools/build-engine.mjs
  ```

- 計算は計算用ブックの上で動かします（`Engine.js`）。そのとき次を差し替えます。
  - 開いているスプレッドシート → 計算用ブック
  - 「今」→ 実行の時刻に固定
  - 乱数 → 種で固定
  - 旧来の計算が作る ID → 種から決まるもの
  - 画面・外部への通信 → 止める

## 新アプリでの予測の実行（段階2-2b）

- 「予測」の画面の「予測を実行」から動かします。予算策定担当（その計画のクライアントの担当でもよい）以上の人が使えます。
- 次の2つの処理が続けて動きます（`Forecast.js`）。
  1. 計算: データ本体から計算用ブックを組み立て、旧来の予測（A-9）を動かし、書き換わったシートの控えを取る
  2. 保存: 計算の間にデータ本体が変わっていないことを確かめてから、控えをデータ本体へ戻す
- 種（乱数）は実行の ID、「今」は実行を始めた時刻です。結果は `FORECAST_RUNS`（1回1行）と `FORECAST_MONTHLY`（月ごと）に残ります。
- 旧来の計算が入力の確認（極端な入力値など）を求めたときは、何も保存せずに画面で内容を見せ、続けるときだけもう一度動かします。
- 履歴の表（`FORECAST_SNAPSHOT` など）は、足された行だけを書きます。

## 計画の画面（段階2-3）

「予測」の画面のタブで、旧来の Web アプリと同じ中身を見て、保存・実行します（`Plan.js`）。見るのは社内全員です。

| タブ | 見るもの | 保存・実行（役割） |
|---|---|---|
| 予測と予算 | 最新の予測（下振れ・中心・上振れ）、月ごとの予算（採用予測・上乗せ・最終予算） | 予測の実行・予算の保存（予算策定担当） |
| 根拠 | 過去の売上だけの予測との差、入力と AI の押し、補正、AI の見立て、前回からの変化 | （見るだけ） |
| 入力 | 製品・メーカー全体・見解・スポット案件 | 入力の保存（予算策定担当。種類ごとに全部書き換える。旧来と同じ） |
| 振り返り | 精度の天気、精度の推移、人の記入（学習インサイト）、AI の見直し案 | 実績を取り込む（管理者）、当たり具合を計算・外れの原因を整理・補正を学び直す・見直し案を作る・記入の保存（予算策定担当）、「承認して反映」＝見直し案の承認の保存と反映を続けて（承認者） |
| 公式版 | 今の公式版・承認待ち・版の一覧と比べ | 公式版として出す（予算策定担当）、承認・却下（承認者） |
| 進み | 手順ごとの状態（実行する順・手順の記号は出さない）、担当者（見るだけ）、この計画の最近の操作 | 売上を取り込む（管理者）、月ごとに集計・市場を調べる（予算策定担当） |

- 見る: データ本体から読むだけのブックを組み立て、旧来の `webGetBootstrap_` をそのまま動かします（計算用ブックは使わない）。入力が同じ間は 6 時間覚えておきます。旧来が書く数式は OUTPUT の予算の列（`=SUM(..)` と `=H+I`）だけなので、その 2 つだけを計算します。
- 保存: 使うシートだけを計算用ブックに組み立て、旧来の `webSave*` をそのまま動かし、変わったシートをデータ本体へ戻します（1 つの裏の処理）。画面を開いた後にほかの人の操作でデータが変わっていたら止めます。
- 実行: 予測と同じく、組み立て → 計算 → 保存の 3 つの裏の処理で戻します（組み立ては 1 回の上限に収まらなければ何回かに分かれる）。計算用ブックは処理の印（`APP_SCRATCH_OWNER`）で、組み立てたままかを確かめます。
- 書き込みは保存の控え（`Journal.js`）を置いてから行います。書き終えた後の表の中身をシステムのフォルダのファイルに置き、書き終えたら消します。途中で止まったら（時間切れ・Google 側のエラー）、次の書き込みの前か、画面の「保存の続きを書く」（`SYSTEM.RECOVER`）で控えのとおりに書き直します。止まっている間は、計画の画面の中身を出しません。
- 「=」（と、「+」「-」の後に英字や括弧が続くもの）で始まる入力は受け付けません。計算用ブックは所有者の権限で動くので、外部を読む数式（IMPORTXML など）を動かさないためです。
- 記録は `PLAN_ACTIONS`（1 回 1 行）と操作の記録（保存した中身も残す）。旧来の操作の記録（`webAudited_`）と管理者の判定（`webActor_`）だけは新アプリが行うので、包んだ中で差し替えています。
- 売上・検証用実績の取り込み（A-2・B-1）の元は業務の設定の「ZAC の実績のスプレッドシート」（所有者が `apiOwnerTask` の `saveSetting`（`key` は `source.zac_spreadsheet`）で URL を入れると、開けるスプレッドシートかを確かめて ID で持つ）。未設定なら取り込まない（旧来のコードにある既定のファイルには頼らない）。
- 担当者（A-1 のうち担当者だけ）は CONFIG!B4 と計画の表（PLANS）の両方に書く。画面では変えない（所有者が `apiOwnerTask` の `setPeople` で変える）。クライアントと年度は計画で決まる。

## 暫定実績・着地見込み・見通しの空模様（2026-10-06 村井さん決定・v0.27.0・@61 公開）

計画ごとにサーバーで計算し、計画の一覧・ホーム・分析に渡します（`Landing.js`・`Portfolio.js`）。旧来の予測の計算は変えません。

- **締まった月**: 実績の取り込み（B-1）を動かした月より前の、年度の月です。B-1 の後に検証の更新（B-2）が成功しているときだけ数えます（B-2 が B-1 より古い・失敗しているときは、締まった月を数えません）。B-1 を動かした月とその後の月の実績（途中の月）は使いません。
- **暫定実績** = 締まった月の実績の合計です。ZAC に記録の無い締まった月（検証の表の実績が空）は 0 円として数えます。
- **着地見込み** = 年度の着地の統計的な推定です。締まった月の実績に、残りの月の予測（P50）を足します。残りの月の予測は、締まった月の実績が予測より上か下かを見て補正します。補正の強さ（実績の重み）は、締まった月が多いほど・予測の幅（P10〜P90）が狭いほど強く、新しい月ほど重く見ます。補正のぶれやすさと予測の幅の倍率は、全計画の締まった月から学びます（学べるまでは決まった値）。締まった月の売上の合計が 0 円の計画（雪）は、この学びに入れません（ほかのメーカーの着地見込みを動かさないため。0 円の月がいくつかあるだけの計画は入れます）。
  - あわせて、80% の幅（8 割の確率でこの間に着地する、という下と上）と、予算以上で着地する確率を出します。
  - 予算は、承認済みの公式版の最終予算、無ければ今の予算（採用予測＋上乗せ）です。予算が下書きの間は採用予測が予測の中心（P50）なので、年度の始め（締まった月が無い間）は着地 ÷ 予算が 1 に近く、上乗せの分だけ動きます。月が締まると、実績が予測から外れた分だけ 1 から離れます。
  - 12 か月が締まった年度の着地見込みは、実績の合計そのものです。
- 実績の取り込みが遅れている（下の表の「霧（実績の遅れ）」の条件に当たる）ときは、空模様が霧（予算が無い）・雪でも、着地見込みの数字を出しません（古い実績のままの数字を見せない。合計にも入れません）。
- 着地見込みの合計は、着地見込みのある計画だけを足します。ホームの合計（`appHomeTotals_`）は、足した計画の数（`landingPlans`）と、着地 ÷ 予算に入れた計画の数（`ratioPlans`）も返します。分析の合計の項目は `appCrossMaker_` の説明のとおりです（`totals.plans` は年度の全計画の数で、着地を足した数ではありません）。

見通しの空模様は、上の行から順に見て、最初に当てはまったものです。

| 空模様 | 決め方 |
|---|---|
| 霧（予算が無い） | 年間予算が無い・0 以下。着地見込みの数字は出します（着地 ÷ 予算と確率は出しません。実績の取り込みが遅れているときは出しません） |
| 雪 | 予算があり、締まった月の売上の合計が 0 円 |
| 霧（予測が無い） | 月の予測（P10・P50・P90）が欠けている・予測の合計が 0（12 か月締まった年度は除く） |
| 霧（実績の遅れ） | 今日までに締まっているはずの年度の月のうち、3 か月以上の実績が取り込まれていない。古い実績のままの数字を見せないよう、着地見込みの数字も出しません（合計にも入れません） |
| 天変地異 | 急な変化。①ひと月の大きな外れ（その月の前までの実績で立てた見込みから 3 標準偏差以上）②2 か月続いた同じ向きの外れ（2 標準偏差以上）③前提の変化（直近 2 回の予測の年間 P50 が 30% 以上違う。31 日以内・差が予算の 10% 以上・締まっていない月があるときだけ）。①②は着地 ÷ 予算が 0.05 以上動いたときだけ。上向き・下向きも返します |
| 猛暑 | 着地 ÷ 予算が 150% 以上 |
| 快晴 | 110% 以上 150% 未満 |
| 晴れのち曇り | 90% より上 110% 未満 |
| 曇り | 50% より上 90% 以下 |
| 雨 | 50% 以下 |

**注意（B-1 を動かす時期）**: 締まった月は「B-1 を動かした月より前の月」です。月の初めの数日、前の月の ZAC の計上が終わる前に B-1 を動かすと、前の月が途中の実績のまま締まった月として数えられます。その月の実績が少なく見えるので、天変地異（下向き）や雪になることがあります。B-1 は、その月の経理の締め（前の月の計上が終わった後）に動かしてください。

## 毎日の手入れ・バックアップ・異常の通知（v0.23.0・@48 公開済み）

- バックアップは毎日の定時実行でデータ本体の複製を作り、バックアップのフォルダに新しい 14 世代を残します。それより古い複製はアーカイブのフォルダへ移します（名前・ID・中身はそのまま。ゴミ箱には送りません）。アーカイブのフォルダが見つからないときは複製を作る前に止まります。
- 毎日の定時実行のトリガー（`triggerDailyBackup`、3 時ごろ）は、**所有者が画面を開いたときに無ければ自動で作ります**（2026-10-07 村井さん承認。確かめるのは 1 日 1 回・あるトリガーには触らない・トリガーの上限 20 に裏の処理の分の余裕が無ければ作らない・開いたときにバックアップそのものは取らない）。作った・作れなかったことは実行ログ（種類 `BACKUP.ENSURE`）に残ります。自動で作らないようにするときは、スクリプト プロパティ `BACKUP_AUTO_ENABLE` を `false` にします（あるトリガーは消しません）。
- 定時実行で異常があったとき（バックアップの失敗・手入れの失敗・監査の鎖の切れ・終わりの無い開始の記録・書きかけの控え・24 時間のエラー）は、所有者と「全体・管理者」の役割が有効な人へメールで知らせます（`Notifications.js`。1 日・同じ異常の組み合わせごとに 1 通まで。本文は異常の種類の名前だけで、名前・数字・ID・メールアドレスは入れない）。
- 通知は**定時実行（`triggerDailyBackup`）の中だけ**で送ります。所有者が `apiOwnerTask` の `runBackup`・`runHousekeeping` で手動で動かしたときは送りません。
- **2026-10-06 村井さんの判断で、通知メールの許可は出していません**（異常はホームのよみのセリフと、所有者が `apiOwnerTask` の `health`・`listAudit` で確認します。「記録と状態」の画面は 2026-10-06 に外しました）。許可が無い間は送信が失敗として記録されるだけで、定時処理の結果は変わらない設計です。次の手順は、将来メールを使う場合のものです。なお `appAuthorizeMaintenance_` は名前が `_` で終わるため、エディタの実行の一覧に出ません。使う場合は所有者だけの入口（`apiAuthorizeAi` と同じ形）を足す必要があります（要承認）。
- メールを送る権限（scope: `script.send_mail`）を足したので、**所有者が 1 回、許可を確認する操作が要ります**。Apps Script エディタで関数 `appAuthorizeMaintenance_` を選んで実行し、Google の許可の画面でメールを送る権限を認めてください（この関数はメールを送りません。許可があることを確かめるだけです）。確認するまで通知は届きません（実際に届くかはまだ確かめていません）。
- なお、メールの送信と「送った」控えの記録は別の操作です。送信または保存場所の障害の途中では、重複して届いたり・届かなかったりする可能性があり、厳密に 1 回だけ届くことは保証しません。

## 年度の締め（v0.24.0・@49 公開済み）

- 所有者が `apiOwnerTask` の `yearPreview` で今年度より前の年度を確かめ（`canClose`・計画の数 `planCount`・行の数 `rowCount`・控えの大きさ `bytes`・指紋 `inputHash`）、その `inputHash` を渡して `yearClose` で締めます（裏の処理として動きます。`OWNER_TASK` が `jobStatus` に置き換わるので、もう一度実行すると結果が分かります）。今年度や未来の年度は締められません。手順は「所有者の操作（エディタから）」にあります（「記録と状態」の画面は 2026-10-06 に外しました）。
- 締めると、その年度の計画と関係する表の行を写した年度の控え（JSON・上限 8MB）をアーカイブのフォルダへ 1 ファイル残し、読み直して一致を確かめてから、年度を閉じた記録を 1 行だけ足します。**元の行は動かさず・消さず・隠さず**、その年度は全部の書き込み経路で読み取り専用になります（画面には「凍結」の印が出ます）。開き直す操作はありません。
- 締められるには、その年度の全部の計画に承認済みの公式版が要ります。保存の控え・承認待ち・動いている処理があると止まります。自動では締めません。実際の年度を締める操作はまだしていません。

## 市場の動きの自動収集（A-4 AI 調査を週 1 回。2026-10-06 村井さん承認「週1回自動」・v0.27.0・@61 公開）

- **計画ごとに週 1 回**: 進行中・今年度か来年度・年度を締めていない計画のうち、最後の A-4 から 7 日を過ぎた（一度も無い）計画を、古い順に集め直します。画面から A-4 を動かした計画は、そこから 7 日たつまで自動では動かしません。A-4 以外の操作（取り込み・予測・学習の反映など）は、今までどおり手で動かします。
- **時間**: 毎日 4 時半ごろ（4:15〜4:45 のどこか）の定時実行（`triggerAutoResearch`、所有者として動く）が、いちばん古い計画を 1 つ選び、画面から始めるのと同じ裏の処理で A-4 を動かします（`AutoResearch.js`）。権限の確かめと監査の記録は画面から始めたときと同じです。
  - 3 時台の毎日のバックアップと手入れ（`triggerDailyBackup`）とはロックを取り合うので、時間を分けています。始めてよいのは 4:00〜7:00 の間だけです。
  - 毎日のバックアップのトリガーがあるときは、その日の手入れが終わって 5 分たつまで始めません（手入れの控え `APP_HOUSEKEEPING` の時刻で見ます）。手入れが遅れた日は、その晩は見送ります。
  - 自動で始めた A-4 が終わったら（成功でも失敗でも）、7 時より前なら次に古い計画を続けて始めます（1 晩 12 計画まで）。ほかの処理が動いている・待っているときは何もしません。
- CONFIG の `AI_RESEARCH_ENABLED` が 0・Vertex の設定が無い・A-2 売上の取り込みが済んでいない計画は飛ばして、同じ回で次の計画を探します（1 回に 20 計画まで）。自動で失敗した・飛ばした・権限が足りなかった計画は 3 日あけてから試します。
- トリガーは毎日の手入れと、所有者が画面を開いたとき（確かめるのは 1 日 1 回）に、無ければ作ります（トリガーの上限 20 に余裕が無ければ作りません）。前の版で作った 1 時ごろのトリガーは、新しい版で最初に確かめたときに 1 回だけ消して 4 時半ごろで作り直します（確かめた控え `APP_AUTO_RESEARCH_CHECKED` の時刻の版で見ます）。
- **止めるとき**: スクリプトのプロパティ `AUTO_RESEARCH_ENABLED` を `false` にします（トリガーは残っても何もしません。止めている間は新しく作りません）。プロパティを消すと元に戻ります（トリガーが無ければ、次の確かめで作ります）。
- 毎回の結果は実行ログ（種類 `AUTO.RESEARCH`）に残り、管理者のホームの仕組みの状態（`system.autoResearch`）に、時間・最後の回・最後に始めた計画・結果・7 日の失敗の数・古いままの計画が、画面の名前（`statusLabel`・`reasonLabel`）つきで出ます。状態の控え（`APP_AUTO_RESEARCH`）は約 8000 バイトより小さく保ちます（失敗の理由は要点 40 字まで。失敗の文そのものは実行ログに残ります）。

見送った・飛ばした理由（`reason`）の意味:

| 印 | 意味 | すること |
|---|---|---|
| `DISABLED` | 止めるスイッチが切ってある | 動かすなら `AUTO_RESEARCH_ENABLED` を消す |
| `BEFORE_HOURS` / `AFTER_HOURS` | 4 時より前・7 時を過ぎた | なし（次の晩に続く） |
| `MAINTENANCE_PENDING` | 今日の毎日の手入れがまだ終わっていない | 続くときは「状態」で手入れの結果を見る |
| `BUSY` | ほかの処理が動いている・待っている | なし |
| `NIGHT_LIMIT` | 1 晩に始める上限（12 計画）に達した | なし（次の晩に続く） |
| `NO_STALE_PLAN` | 7 日を過ぎた計画が無い（試してから 3 日たっていないものは除く） | なし |
| `NOT_READY` | 準備ができていない（`AI_DISABLED` AI 調査が無効・`VERTEX_CONFIG` Vertex の設定が足りない・`NO_SALES_DATA` A-2 が済んでいない・`NO_SETUP` CONFIG が無い） | 計画の設定を直すか、そのままにする（3 日ごとに確かめ直す） |
| `DENIED` | 頼んだ人（所有者）に、その計画の A-4 を動かす権限が無い | 役割を確かめる |
| `START_FAILED` / `FAILED` / `STALLED` | 始められなかった・A-4 が失敗した・途中で止まった | 実行ログとエラーログで理由を見る（7 日の失敗の数に入る） |

## 所有者の操作（エディタから）

管理の画面（設定・メンバーと役割・表示名・記録と状態・年度の締め・計画の作成・全計画での学習）は画面から完全に外します（2026-10-06 村井さん決定）。これらの操作は、所有者が Apps Script のエディタから `apiOwnerTask` で行います（`OwnerTask.js`）。エディタから実行する関数には引数を渡せないので、頼む操作はスクリプト プロパティ `OWNER_TASK` に JSON で書きます。

**先に読む注意**

- **`APP_` で始まるキーには触らないでください。** 同じスクリプト プロパティに、アプリの状態（監査の鎖の最新のハッシュ・書きかけの保存の控え・裏の処理の記録・社内のドメイン・データ本体の ID など）が入っています。書き換えたり消したりすると、監査の鎖が切れて改ざんに見えたり、処理の記録や保存の控えが古い状態に戻ったりします。所有者が触るのは `OWNER_TASK` だけです（`OWNER_TASK_RESULT` は結果の置き場です。自動の AI 調査を止めるときだけ `AUTO_RESEARCH_ENABLED` も、毎日のバックアップのトリガーを自動で作らないようにするときだけ `BACKUP_AUTO_ENABLE` も使います）。
- **裏の処理が動いている間は、スクリプト プロパティを編集・保存しないでください。** 「スクリプト プロパティを保存」は、編集の画面を開いたときの値を全部書き戻すおそれがあり（実際の動きはまだ確かめていません）、その間に処理が書き換えた `APP_` のキーを古い値に戻してしまいます。処理を始めると `OWNER_TASK` は自動で `jobStatus` に置き換わるので、結果はプロパティを触らずに `apiOwnerTask` をもう一度実行すれば分かります。定時処理が動く夜中から早朝（AI 調査・バックアップ・手入れ）も避け、編集の画面を開いたらすぐに保存してください。
- **スクリプトの編集権限がある人は、エディタから実行すると所有者として扱われます。** Apps Script では、エディタから実行した人がそのまま実行する人になるためです（`apiSetup` など、所有者だけの入口も同じです）。スクリプトの編集権限は所有者だけにしてください。画面（ウェブアプリ）から呼ばれた場合など、実行する人が所有者でなければ断り、断ったことを記録に残します。

**手順**

1. Apps Script のエディタで「Trends2Targets」のプロジェクトを開きます。
2. 左の「プロジェクトの設定」（歯車）を開き、いちばん下の「スクリプト プロパティ」で「スクリプト プロパティを編集」→「スクリプト プロパティを追加」を押します。
3. プロパティに `OWNER_TASK`、値に下の表の JSON を 1 行で入れ、「スクリプト プロパティを保存」を押します（すでにあるときは値だけ書き換えます）。
4. 左の「エディタ」で `Api.gs` を開き、上の関数の一覧から `apiOwnerTask` を選んで「実行」を押します。
5. 下の「実行ログ」に結果が出ます。同じ結果（大きいときは要約）がスクリプト プロパティ `OWNER_TASK_RESULT` に入ります（「プロジェクトの設定」を開き直すと見えます）。`"ok": true` ならうまくいっています。`hint` に、すぐに終わったのか、裏の処理を始めたのか（まだ終わっていないのか）が書いてあります。
6. うまくいった後の `OWNER_TASK` は、操作の種類で変わります。
   - 読むだけの操作（`listDirectory`・`listSettings`・`listPlans`・`planCandidates`・`health`・`listAudit`・`yearPreview`・`poolPreview`・`jobStatus`）: そのまま残ります。もう一度実行すると読み直します。
   - 書く操作（`saveMember`・`grantRole`・`revokeRole`・`saveClientName`・`saveClient`・`saveSetting`・`enableBackup`・`runBackup`・`runHousekeeping`・`verifyAudit`）: すぐに終わり、`OWNER_TASK` は消えます（同じ操作を 2 度動かさないため）。
   - 裏の処理を始める操作（`createPlan`・`setPeople`・`yearClose`・`poolApply`）: `OWNER_TASK` が `{"action":"jobStatus","jobId":"JOB-…"}` に置き換わります。1〜2 分おいて、プロパティは触らずに `apiOwnerTask` をもう一度実行すると、処理の結果（`status` が `DONE` か `FAILED`。`FAILED` なら `error` に理由）が分かります。短い処理は、始めたその場で終わることもあります（`hint` に「すぐに終わりました」と出ます）。
   - 実行している間に `OWNER_TASK` が書き換えられていたときは、消しも置き換えもしません。
7. 失敗したときは `"ok": false` と理由（`error`）が入り、`OWNER_TASK` は残るので、直してもう一度実行します。

**値の写し方**

- 中で使う関数・権限の判定・入力の確かめは、画面の操作と同じです。書く操作は画面と同じ操作の名前（`SETTING.SAVE`・`ROLE.GRANT`・`CLIENT.SAVE` など）で操作の記録に残り、理由の欄に「OWNER_TASK（エディタから）」と入ります。
- `roleId`・`clientId`・`rowVersion` は `listDirectory`、`planId` は `listPlans`、ZAC の名前は `planCandidates` の結果から写します。
- `rowVersion` は、ほかの変更を上書きしないための行の版です。空にすると確かめずに書くので、必ず `listDirectory` の結果から写してください。
  - `saveMember` は `members[].rowVersion`、`revokeRole` は `roles[].rowVersion` を写します。
  - `saveClientName` は `clients[].rowVersion`（表示名の行の版）を写します。まだ表示名を決めたことがないメーカーだけ空（`""`）です。
  - `saveClient` は `clients[].clientRowVersion`（メーカーの行の版）を写します。
- `saveClient` は、`clientId` を省くとメーカーを足し、`clientId` を入れると直します。直すときは全部の項目（`clientName`・`zacCode`・`isActive`・`note`・`rowVersion`）が要ります（省いた項目が空や有効に戻らないよう、足りなければ何もせずに止まります）。今の値は `listDirectory` の `clients[]`（`zacName`・`zacCode`・`active`・`note`）から写し、変えたい項目だけ変えます。`isActive` は `true` か `false`（`""` で囲まない）です。`clientName` は売上の取り込みで ZAC と照らし合わせる名前なので、画面に出す名前を変えるときは `saveClientName` を使います。
- `createPlan`・`yearPreview`・`yearClose` には年度 `fy`（4 桁の数。例 `2027`）が要ります。無い・4 桁でないときは、何も始めずに止まります。
- 年度の締めは、必ず `yearPreview` で `"canClose": true` を確かめ、出た `inputHash`（64 桁）をそのまま `yearClose` に渡します。確認の後に年度の中身が変わっていれば、締めずに止まります。
- `listAudit` は、`limit` を省くと新しい 200 行までです（最大 2000）。結果が長すぎて実行ログに全部を出せないときは、`OWNER_TASK_RESULT` の `note` にそう書いてあるので、`limit` を小さくするか、`month`・`query` で絞ってもう一度実行します。
- `health` の `ok` は、`warnings` に 1 つでも要確認（表の問題・監査の鎖・監査の最後の行が消えた疑い・バックアップが無効か 26 時間より古い・手入れの要確認・書きかけの保存・年度の一覧を読めない）があれば `false` です。手入れのときの 24 時間のエラーの数（`housekeeping.errors`）と終わりの無い開始の数（`housekeeping.openStarts`）も出ます。

| 操作 | すること | `OWNER_TASK` の例 |
|---|---|---|
| `listDirectory` | メンバー・有効な役割・メーカー（ID・ZAC の名前とコード・表示名・行の版）を見る | `{"action":"listDirectory"}` |
| `saveMember` | メンバーを登録する・直す（社内のメールだけ） | `{"action":"saveMember","email":"name@bigm2y.com","displayName":"山田 太郎","department":"営業部"}` |
| `grantRole` | 役割を付ける（`PLANNER`・`APPROVER`・`ADMIN`。`scopeType` は `ALL` か、予算策定担当だけ `CLIENT`） | `{"action":"grantRole","email":"name@bigm2y.com","role":"PLANNER","scopeType":"CLIENT","clientId":"CL-…"}` |
| `revokeRole` | 役割を外す（行は残して無効にする） | `{"action":"revokeRole","roleId":"RL-…","rowVersion":1}` |
| `saveClientName` | メーカーの画面の名前を決める（空にすると自動の名前に戻す） | `{"action":"saveClientName","clientId":"CL-…","displayName":"サンプル製薬","rowVersion":1}` |
| `saveClient` | メーカーを足す（`clientId` なし）・直す（`clientId` と全部の項目。無効にするのは `"isActive":false`） | `{"action":"saveClient","clientId":"CL-…","clientName":"（ZAC の名前）","zacCode":"","isActive":false,"note":"","rowVersion":1}` |
| `listSettings` | 業務の設定を見る | `{"action":"listSettings"}` |
| `saveSetting` | ZAC の実績のスプレッドシートを決める | `{"action":"saveSetting","key":"source.zac_spreadsheet","value":"https://docs.google.com/spreadsheets/d/…/edit"}` |
| `listPlans` | 計画の一覧（`planId`）を見る | `{"action":"listPlans"}` |
| `planCandidates` | 計画を作れるメーカーの候補（ZAC の名前）を見る（`"refresh":true` で ZAC を読み直す） | `{"action":"planCandidates"}` |
| `createPlan` | 計画を作る（裏の処理） | `{"action":"createPlan","clientName":"（ZAC の名前）","fy":2027,"peopleCsv":"山田,佐藤"}` |
| `setPeople` | 計画の担当者を変える（裏の処理） | `{"action":"setPeople","planId":"PL-…","peopleCsv":"山田,佐藤"}` |
| `enableBackup` | 毎日のバックアップを有効にする（ふだんは所有者が画面を開いたときに自動で有効になる。`BACKUP_AUTO_ENABLE` で止めているとき・自動で作れなかったときに使う） | `{"action":"enableBackup"}` |
| `runBackup` | 今すぐバックアップを取る | `{"action":"runBackup"}` |
| `runHousekeeping` | 毎日の手入れを今すぐ動かす | `{"action":"runHousekeeping"}` |
| `verifyAudit` | 監査の鎖を全部の月で確かめる | `{"action":"verifyAudit"}` |
| `health` | 状態の要約（`ok`・`warnings`・問題のある表・監査・バックアップ・手入れ・保存の控え・年度） | `{"action":"health"}` |
| `yearPreview` | 年度を締められるか確かめ、指紋（`inputHash`）を受け取る（何も書かない） | `{"action":"yearPreview","fy":2025}` |
| `yearClose` | 確かめた指紋で年度を締める（裏の処理。元に戻せません） | `{"action":"yearClose","fy":2025,"inputHash":"（yearPreview の inputHash）"}` |
| `poolPreview` | 全計画の情報源の信頼度の事前分布を見比べる（書かない） | `{"action":"poolPreview"}` |
| `poolApply` | 事前分布を各計画に書く（裏の処理） | `{"action":"poolApply"}` |
| `listAudit` | ログを見る（`kind` は `AUDIT`・`RUN`・`ERROR`、`month` は `yyyy_MM`、`query` で絞る、`limit` は既定 200・最大 2000） | `{"action":"listAudit","kind":"AUDIT","month":"2026_10","query":"ROLE"}` |
| `jobStatus` | 裏の処理の結果を見る（裏の処理を始めると、`OWNER_TASK` は自動でこの形になる。`jobId` を省くと、最後に始めた処理） | `{"action":"jobStatus","jobId":"JOB-…"}` |

## 利用者・管理者の運用手順

現在は所有者だけが開けます（MYSELF）。役割の判定はローカルで検証済みですが、社内の複数人での実運用は未確認です。

| 役割 | 画面と操作 |
|---|---|
| 閲覧・情報提供 | ホーム・メーカー・予測（予測・予算・根拠・検証・公式版）・分析・学びを読む。入力の保存は予算策定担当以上です |
| 予算策定担当 | 入力と予算を保存、予測を実行、公式版として出す、検証と月次学習を更新。クライアント限定の付与では対象の計画だけ書けます |
| 承認者 | 公式版を承認・却下、四半期レビューを判断・適用。既存の役割階層では予算策定担当の操作も含みます |
| 管理者 | 売上・実績の取り込み（予測の画面の「進み」「検証」）。計画作成・設定・メンバーと役割・状態・バックアップ・年度締めは、管理の画面を外したので所有者が Apps Script のエディタから `apiOwnerTask` で行います（所有者でない管理者は画面からはできません） |

### 1 年の流れ

1. 所有者が `apiOwnerTask` で、必要なメーカー（`saveClient`）と計画（`createPlan`。年度と担当者）を登録します。年度は4月開始の年で呼びます（FY2026 は2026/04〜2027/03）。
2. 管理者が「進み」で売上取込（A-2）、策定担当が売上加工（A-3）・AI調査（A-4）を実行します。実績の取得元は、所有者が `saveSetting` で決めた業務の設定（ZAC の実績のスプレッドシート）を使います。
3. 策定担当が入力・予測・予算を整え、「公式版」で提出します。承認者が数字を確認して承認・却下します（自分の提出を承認する扱いは既存ルールに従います）。
4. 実績が締まったら（前の月の ZAC の計上が終わってから。「暫定実績・着地見込み・見通しの空模様」の注意）管理者が「検証」で実績取込（B-1）、策定担当が検証更新・指標更新・見立て更新・月次学習（B-2〜B-5）を順に行います。インサイトの記入も保存します。
5. 四半期ごとに提案を作り（C-1）、承認者が判断し、承認した提案を適用します（C-3）。
6. 次年度は新しい計画として作ります。終わった年度を締める場合だけ、所有者が `apiOwnerTask` の `yearPreview` で内容を確認し、`yearClose` で年度を締めます。現在・未来の年度は締めません。行の移動・凍結解除は行いません。

### 管理者の点検と障害対応

- 所有者が `apiOwnerTask` の `saveMember`・`grantRole`・`revokeRole` で社内のメンバーと役割を登録し、`listDirectory` で役割・対象メーカー・有効期間（`validFrom`・`validTo`）を確認します。所有者は常に管理者です。付与の無効化と公開範囲の変更は別の操作です。
- 所有者が `apiOwnerTask` の `health` で保存の控え、処理、監査、バックアップ、手入れを確認し、`listAudit` で操作の記録・実行ログ・エラーを見ます。処理中の重複依頼は断られるので、終わったのを確かめてから（画面は読み直す。エディタからは `jobStatus`）再試行します。古い画面で保存が止まった場合も読み直します。
- 書きかけの保存は、控えの内容を確認して予測の画面の「保存の続きを書く」で復旧します（全体の予算策定担当以上の権限が必要）。凍結記録や控えが壊れている場合は書き込みを止めたままにし、控えを削除して強行しません。
- 日次バックアップは新しい14世代をバックアップフォルダに残し、古い世代と月次の写しはアーカイブに残します。正常な日は通知メールを送りません。通知の権限確認は前の節の `appAuthorizeMaintenance_` を使い、配送確認のために無断のテストメールや意図的な障害を起こしません。

### バックアップからの復元

自動復元の操作は未実装です。まず現在のデータと凍結記録を別の控えとして保全し、復元候補の年度・計画・列・キー・型・数式・書式・凍結記録を読み取りだけで照合します。古いバックアップには年度の締めの記録が無い可能性があるため、丸ごとの差し戻しで締めた年度を開かないようにします。

データ本体の差し替え、保存先の切り替え、行の書き戻しは、具体的な復元設計と村井さんの承認後に行います。凍結記録の表が読めない場合は空で作り直さず、元の記録を戻す方針を先に確認します。元データ・候補ファイルは削除・ゴミ箱送りをしません。

## コードの約束

- 公開する関数（ブラウザから `google.script.run` で呼べる関数）は `Api.js` の `doGet`・`api*`・`trigger*` だけ。どれも本体は `return api_(...)` だけにし、本人確認 → 役割 → 記録つき実行 → エラーの記録 を必ず通す。それ以外の関数は名前の末尾を `_` にする。
- 書き込みは開始を記録できなければ実行しない（fail-closed）。記録はハッシュの鎖でつなぎ、所有者が `apiOwnerTask` の `health`（今月）・`verifyAudit`（全部の月）で改ざんを点検できる。
- 表の列は `Schema.js` だけで決める。データ本体の 1 行目が定義と違えば書き込みを止める。列を変えるときは版を上げて移行する。
- `Assets.js` は自動生成（`cd ../assets/characters/src && python3 build.py`）。手で編集しない。
